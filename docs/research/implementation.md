# 实现原理与参考架构

本页首先解释公开技术资料能够支持的通用实现，再给出当前仿真项目的参考设计。所有关于 HintonAI 内部栈、性能和算法的描述均未获证实。来源编号见[来源台账](sources.md)。

## 1. 从截图到可执行系统

截图中的复合移动机器人可从功能上拆成 AMR 底盘、机械臂和夹具：底盘把载具送到仪器附近；机械臂完成台面、试管架与仪器之间的取放；夹具适配具体容器。设备外观只能支持这种组成推断，无法确认其硬件型号、定位方式或抓取算法。[S01]

公开实现把这些职责分开处理：Nav2 提供移动机器人的导航体系，MoveIt 通过规划接口生成考虑碰撞及关节限制的轨迹；Open-RMF 解决异构机器人与共享空间、门、电梯等基础设施之间的协作。仪器一侧，SiLA 2 将能力表达为 Feature、Command 和 Property；PyLabRobot 则提供面向其支持仪器的统一 Python 接口。[S02][S03][S04][S05][S06]

因此，实验室控制系统通常包含以下层次。下表是**参考设计**，并非对截图原厂系统的反编译结论。

| 层次 | 负责的事情 | 本阶段的实现边界 |
| --- | --- | --- |
| 控制台与 3D | 创建任务、编辑步骤、显示位置/状态、查询结果 | 浏览器交互和状态可视化 |
| 实验工作流 | 保留实验配方快照，驱动步骤状态与失败处理 | 后端任务状态机与模拟步骤 |
| 资源调度 | 给任务分配可用设备，避免同一设备被重复占用 | 仿真设备占用与排队 |
| 设备适配 | 统一命令、进度、完成、失败等语义 | 当前为模拟驱动；真机驱动另行验证 |
| 实际设备 | 机器人运动、仪器检测、传感反馈 | 本阶段未接入 |
| 数据与追溯 | 样品、任务、步骤、设备和结果的关联 | 保存仿真结果、任务与事件；不冒充实测值 |

## 2. 一次实验的完整执行链

以下以“从样品架取样、送入仪器、检测并归位”为参考例子：

1. 用户在控制台选择或编辑流程，绑定样品编号、样本数量与目标设备。提交时保存流程快照，防止运行中的任务被后续模板编辑改变。
2. 后端检查步骤参数、设备能力和初始状态。参数不合法则在启动前拒绝；资源暂不可用则进入队列，并明确原因。
3. 调度器选择可执行任务，锁定相关设备。移动机器人前往取样点，仪器接受预约或准备指令。
4. 机械臂在完成定位、容器识别与现场允许条件检查后取放。真实系统必须等待动作完成与必要的传感反馈，不能用界面动画播放完代替成功。
5. 仪器接收样品后启动检测。仪器驱动报告运行状态、完成/失败与结果；任务引擎据此推进后续步骤。
6. 后端记录每一步的开始、结束、设备、样品与结果关联。浏览器订阅状态，更新进度、设备标记和 3D 场景。
7. 仪器或机器人失败时，任务停在可解释的状态，保留错误、已完成步骤和资源状态。恢复前由操作者确认现场情况；对可能重复加液、加热或取放的动作不做无条件重放。

SiLA 官方使用“LIMS 让搬运设备把板放入读板机；收到成功返回后，启动读板；再取回板”的例子解释跨设备编排。这支持上面的“等待设备返回，再推进流程”原则，但并不证明特定厂商实现了同样的调度器。[S02]

## 3. 工作流与资源调度

实验任务是一个持久存在的业务对象。它需要与执行中的设备连接分离，才能回答“这是哪一批样品”“当前卡在哪一步”“取消后设备处于什么状态”。

**参考设计：** 最小系统先用顺序步骤与明确状态机覆盖当前需求；有独立并行分支时再引入有向无环图或更复杂工作流引擎。启动前做参数校验与设备能力匹配，执行时维护占用关系，结束/取消/失败时释放占用并记录事件。

| 状态 | 含义 | 后续处理原则 |
| --- | --- | --- |
| 排队 | 尚未分配到可执行资源 | 保留次序与等待原因 |
| 运行 | 某个步骤正在执行 | 只由执行引擎或设备反馈推进 |
| 暂停 | 在允许的步骤边界或暂停点停止推进 | 保留进度与占用语义 |
| 完成 | 所有必要步骤已成功 | 关联结果并释放资源 |
| 失败 | 出现阻断后续步骤的问题 | 保留失败原因与已完成记录 |
| 取消 | 用户取消或策略终止 | 真机需要确认实际停止，不把撤销请求当作已停止 |

共享设备不能仅靠前端按钮禁用来防重。后端必须作为调度事实源。多机器人进一步涉及交通冲突与充电约束；Open-RMF 官方演示说明了投标式任务分配、冲突消解及电池任务注入。这说明成熟调度比“选一个空闲机器人”更复杂，不表示当前项目已实现这些能力。[S04]

## 4. 移动、对接与抓取

**已查证的能力边界：** MoveIt 的运动请求描述目标关节状态或末端位姿，默认进行碰撞检查；结果为带速度和加速度限制的轨迹，而不仅是几何路径。其插件接口允许不同规划器。[S03] Nav2 负责自主移动导航体系，Open-RMF 负责多车及共享基础设施协作，两者不能互相替代。[S04][S06]

**工程推论：** 仪器操作要求的末端精度往往不能只依靠底盘到站。参考实现需要把“到达工位”和“末端对接/容器抓取”分成两个阶段，并依据设备决定是否使用标记、视觉或机械定位。具体误差预算应由夹具容差、机械臂标定、底盘重复定位与仪器接口共同确定；本次没有可用实测值。

3D 仿真中移动模型与机械臂动画用于表达业务状态。它不包含真实动力学、标定、力控、感知和安全停机验证，不能把画面上的无碰撞当成真机可执行轨迹。

## 5. 仪器接口与适配器

SiLA 2 官方文档说明其以 HTTP/2、Protocol Buffers 与 gRPC 为基础，以功能而非设备类型组织接口。Feature 暴露 Command 和可读取/订阅的 Property；其目的之一是减少设备互操作的差异。[S02]

现实实验室通常还存在厂商 SDK、串口、Modbus、TCP、自定义文件交换等接口。这里列的是**候选适配路线**，不是对任意截图仪器的协议判断：优先使用厂商支持的接口；支持 SiLA 的设备可以接入 SiLA 客户端；PyLabRobot 已支持的设备可评估其 Python 驱动。PyLabRobot 的“统一接口”只覆盖实际支持的设备及能力，不能理解为任意仪器即插即用。[S05]

参考驱动应明确：连接状态、能力清单、命令参数、唯一命令编号、进度、成功结果、失败分类和取消语义。网络响应成功只说明请求被接收；物理动作是否完成仍需具体协议和反馈支持。

## 6. 3D 场景与实时状态

**参考设计：** 设备与机器人都有稳定 ID，3D 模型绑定该 ID。浏览器接收后端的机器人位置、任务状态和设备状态，更新模型、选中面板与日志。控制命令通过后端校验后才进入执行队列；刷新网页不会重新开始实验。

Open-RMF 的官方演示公开了独立 API 服务与 Web 仪表盘的结构，以及 fleet adapter 上报任务和机器人状态的用法。示例与主分支文档出现不同的内部 URL 配置，应按选定发行版核对，不能把某一示例地址当成通用接口合同。这支持“可视化与设备状态链路分离”的路线，不证明本项目使用了 RMF 或原厂采用相同协议。[S04][S08]

浏览器级演示可以用 Three.js 表达实验室设备、移动底盘与机械臂。若要验证运动、传感器与控制器协作，则应另设 ROS/Gazebo 或其他适合硬件栈的仿真环境，并与业务状态机进行联调。两种仿真分别解决用户流程与机器人行为的问题。

## 7. 实验数据闭环与 AI 的位置

“闭环”至少有两层，不能混为一谈：

- **执行与追溯闭环：** 样品输入、操作记录、仪器结果、失败记录相互关联，支持复盘。本项目应先完成这一层的仿真。
- **实验优化闭环：** 算法根据检测结果提出下一组参数，经过边界与批准后再执行。还需定义优化目标、变量范围、停止条件、失败样本处理和效果对照；本次没有截图原厂的算法证据。

AI 可以解释数据或生成候选流程，但执行前仍需要结构化参数校验、设备能力校验与约束检查。当前用户授权的重点是控制台、3D 仿真和任务编排，不要求接入大模型服务；不能因标题含“AI”而伪造模型已接入或自动优化已验证的结论。

## 8. 复刻路线与取舍

| 路线 | 适用条件 | 当前选择 |
| --- | --- | --- |
| 浏览器 3D＋后端模拟 | 验证控制台、状态机、流程编辑和结果追溯 | 本阶段采用 |
| ROS 2＋Nav2/MoveIt＋机器人仿真 | 已有机器人模型，需要验证导航与机械臂行为 | 后续按硬件选择 |
| Open-RMF 多车协作 | 多车、多供应商和共享交通资源成为实际需求 | 当前作为研究参照 |
| SiLA/厂商 SDK/PyLabRobot | 确认具体仪器和支持能力，需要真机联调 | 待设备资料与测试 |

选择最小可运行仿真避免过早安装机器人全栈，也让 UI 与业务问题先获得可验证结果。其限制是：仿真通过只证明本项目相应的软件流程，不能证明实机节拍、精度、避障、安全或实验科学有效性。
